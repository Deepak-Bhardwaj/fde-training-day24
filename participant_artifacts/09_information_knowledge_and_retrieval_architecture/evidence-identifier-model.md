# Evidence Identifier Model

**Case:** Fleet Disruption & Voyage Recovery Intelligence Workbench

## Stage question
How does enterprise evidence become canonical meaning, connected knowledge and runtime context?

## Why this artifact exists
To define the deterministic and universally unique identification strategy for every piece of raw evidence and canonical entity. This ensures idempotent processing (GS-07), prevents duplicate state mutations, and enables precise audit reconstruction.

## Case challenge
Identifiers must be globally unique across both the shore platform and the vessel edge, even when they are disconnected. Relying on centralized, auto-incrementing IDs will fail during offline blackouts (GS-14).

## Minimum content

### 1. Raw Evidence Identification (`EvidenceRecord`)
Every raw piece of data ingested into the system is assigned a deterministic `evidence_id` to guarantee idempotency (GS-07).
- **Formula:** `evidence_id = SHA-256(source_id + observed_timestamp + payload_hash)`
- **Behavior:** If a duplicate or replayed event arrives (due to telemetry clock drift or network retries), the calculated `evidence_id` will match an existing record. The system logs it as `Ignored_Duplicate` and discards the payload, preserving the original record's provenance.

### 2. Canonical Entity Identification
Once raw evidence is transformed into a canonical entity (e.g., `Constraint`, `PolicyRule`), it is assigned a stable identifier.
- **Constraints & Policies:** Composite deterministic keys (e.g., `constraint_id = source_id + external_reference_id`). This ensures that updates from the same source update the existing node rather than creating a duplicate.
- **Disruptions & Recovery Options:** UUID v4. These are unique, transient operational records generated by the engine or human operators.

### 3. Cross-Zone Identity Resolution (Shore vs. Vessel)
- When the vessel edge generates a `RecoveryOption` or `PlanApproved` event offline, it uses a UUID v4.
- Upon reconnect (GS-15), the shore platform ingests this event. Because the UUID was generated at the edge, the shore platform accepts it as the canonical ID for that specific action, preventing ID collisions during the sync merge.
